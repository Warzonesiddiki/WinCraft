# WinCraft project audit — 2026-10-16

**Baseline:** `0861051f45769dab294196cd3fd35af238df027d` (`2.0.0`)  
**Scope:** Desktop React/TypeScript, Tauri/Rust boundary, Express/PostgreSQL backend, website, CI and release tooling. Includes local builds, tests, static checks and npm advisory checks.  
**Limitations:** This is a repository review, not a penetration test. No Windows host, Rust toolchain, PowerShell, production database, deployment configuration or signed release installer was available here. No live service was probed.

## Executive assessment

The project has good foundations: strict frontend TypeScript, a native Rust boundary for system changes, separate main/HUD capabilities, rollback-oriented registry operations, a fail-closed database TLS policy, versioned migrations, transactional account-token changes, and a substantial test suite. The site and backend build locally, and npm reported no known advisories in any of the three dependency trees on the audit date.

**At the audited baseline, this checkout was not release-ready.** I reproduced multiple independent failures in checks wired into the repository's CI/release scripts. Newly added controls and the Skinpacks panel also contained placeholder copy, and an over-broad “configurable” list excluded ordinary controls from bulk restore/history actions. A Windows run is still required to validate registry behavior and the native/elevated code.

The findings and verification table below record the baseline. A follow-up remediation pass was applied afterward; its current status is recorded near the end. At audit time, only this report had been added.

## Findings

### F-01 — P1: shipped UI contains placeholder copy; the Skinpacks regression test fails

**Evidence:** `src/locales/en.ts:1195–1205` (the corresponding block is identical in `it`, `fr`, `es`, `de` and `pt`); `src/components/skinpacks.tsx:81–88`; `src/components/skinpacks.test.tsx:31–34`.

The Skinpacks panel renders literal strings such as **“Skinpacks management,” “Pack body,” “Scope,”** and **“Values summary.”** In particular, the scope line does not state the expected safety boundary (the test requires “does not install”). The same incomplete copy is present in every locale. This is not only a translation-quality problem: users do not receive the feature description or scope warning the component was designed to show.

The live test confirms the defect: `npm run test:coverage` ran 392 tests, with **391 passing and one failure** in `SkinpacksPanel > states what the look is and what it is not` because the rendered scope is just “Scope.”

**Recommendation:** Write real English copy and translations for every Skinpacks field, including a precise statement of what is changed and what is not installed. Keep the test asserting the user-facing claim rather than weakening it.

### F-02 — P1: “configurable” list makes ordinary controls disappear from bulk recovery

**Evidence:** `src/catalog.ts:1–22`; `src/components/tweak-row.tsx:53–65`; `src/App.tsx:580–583, 676–680`; `src/components/change-history.tsx:135–142`; `src/scan-runner.ts:235–263`.

`CONFIGURABLE_TWEAK_IDS` now contains 18 IDs. Only the original three (`ecoqos_rules`, `limit_do_background_download`, `monitor_refresh_profile`) have dedicated cards in `TweakRow`/`AdvancedControlCard`. Eleven additional IDs correspond to ordinary one-switch registry tweaks. Yet the same set is used to exclude “applied” counts, `Restore all`, Change History’s bulk restore, and scan selection. A user can toggle these controls individually, but they are omitted from those bulk recovery paths and the dashboard’s applied count.

The regression is directly reproducible: `npm run test:debloat` fails because `scripts/test-debloat-ui.mjs:77–81` expects exactly the three dedicated-card IDs but finds 18. Four other entries in `src/catalog.ts` also do not match current native catalog IDs (`no_post_login_upsell`, `no_welcome_tips`, `explorer_home_this_pc`, and `menu_show_delay_minimal`); the native catalog instead contains related or differently named IDs.

**Recommendation:** Restrict this set to controls with real dedicated configuration/recovery flows, or implement and test those flows. Add a parity test that maps every special-case ID to an actual native catalog entry and verifies bulk restore/history behavior.

### F-03 — P1: the catalog’s new controls have placeholder names/descriptions across locales

**Evidence:** `src/locales/en.ts:1953–2012` and corresponding `tweaks` blocks in all five other locales; `scripts/audit-i18n.mjs`; `src/components/tweak-row.tsx:67–69`.

`npm run check:i18n-quality` fails with **200 unchanged-English candidates**. The output consists of the new Skinpacks copy plus the names/descriptions for the 15 Browser Only IDs. For example, `ads_in_settings` is labeled “Ads In Settings” with the description “Configuration option.” The same placeholders appear in Italian, French, Spanish, German and Portuguese. Eleven of those IDs are present in the native catalog, so these strings are user-visible; `textFor()` selects the locale entry rather than the more descriptive Rust fallback.

**Recommendation:** Translate the active controls’ real names and consequences, remove unused/stale locale keys, and retain the quality gate. Only add entries to the reviewed-as-correct list for terms that are genuinely identical—not placeholders.

### F-04 — P1: release/public copy says 150 controls while the shipped catalog asserts 161

**Evidence:** `src-tauri/src/lib.rs:2963–2968`; `scripts/check-public-counts.mjs`; README, site copy, Store listings and `release-notes/RELEASE-NOTES-2.0.0.md`.

The native catalog test asserts **161** controls, while public copy continues to say **150**. `npm run check:public-counts` exits non-zero and reports stale counts across the README, site, release notes and all six Store listings; the homepage count check also expects the new total. This makes the published feature count inaccurate and is another CI failure.

**Recommendation:** Confirm 161 is the intended shipped total, then update all current-version public text and generated/homepage stats together. If 150 is the intended product boundary, remove or defer the extra controls and update the catalog test instead.

### F-05 — P2: Browser Only research rows conflate distinct shell settings and current control ownership

**Evidence:** `src-tauri/src/tweaks.rs` (`ads_in_settings`, `disable_start_suggestions`, `quick_access_no_cloud`, `snap_assist_off`); `src-tauri/src/settings_tweaks.rs` (`disable_windows_suggestions`, `explorer_open_this_pc`); Part B of `docs/BROWSER-ONLY-PACK.md`.

The Browser Only table originally mixed desired effects with current control ownership. `SubscribedContent-353694Enabled` and `SubscribedContent-353696Enabled` are owned by `disable_windows_suggestions`; `SubscribedContent-338388Enabled` is owned by `disable_start_suggestions`, and it is a Start-suggestion value rather than a Welcome value. The current composite also writes the Windows Welcome value `SubscribedContent-310093Enabled`, the finish-setup value `ScoobeSystemSettingEnabled`, and the tips value `SubscribedContent-338389Enabled`. `ShowRecent` and `ShowFrequent` control recent-file/frequent-folder history, separate from the cloud/account-content preference named by `quick_access_no_cloud`; those values are not required for that control's stated effect. Likewise, opening Explorer on This PC and hiding the Home navigation node are separate behaviors. The Snap Assist suggestion setting and the Snap Layouts maximize-hover flyout are also distinct; sources use conflicting registry names for the latter (`SnapAssistFlyout` versus `EnableSnapAssistFlyout`). No extra registry write should be inferred from this research table without Windows validation.

The native preview is generated from actual writes, so unclear ownership or overbroad descriptions can still mislead users even when rollback is correct. The current code should keep the cloud-only control scoped to cloud content; add history visibility or Home/flyout behavior only as separate, validated features.

**Recommendation:** Document ownership and distinct effects precisely, keep unvalidated values explicit, and only expand a control after checking the intended effect on supported Windows builds. Pin exact current write sets in mock-registry tests.

### F-06 — P2: keyboard settings target the Mouse registry key

**Evidence:** `src-tauri/src/tweaks.rs:1203–1226`.

Both `keyboard_delay_zero` and `keyboard_speed_fast` write under `HKCU\Control Panel\Mouse`. Windows’ keyboard repeat settings are stored under `HKCU\Control Panel\Keyboard`. As written, applying these controls can create/snapshot values at the wrong location and report success without changing the keyboard settings.

**Remediation:** These two legacy IDs are now restore-only: their definitions remain available to roll back snapshots created by older versions, but new applications are rejected, profiles and Scan exclude them, and they are omitted from active counts. The Rust list returns one only while its snapshot exists so a user can restore it. The supported combined `reduce_keyboard_delay` control owns `HKCU\Control Panel\Keyboard`. Native regressions pin that owner, rejected reapplication, rollback of old snapshots, profile-import rejection, and Scan exclusion. Windows behavior remains unverified here; do not repoint old snapshot metadata in place.

### Deployment constraint — proxy identity and rate-limit state are process-local

This is a deployment assumption, not a verified production incident. `backend/src/proxy-policy.ts` defaults proxy trust to off, while auth/public-form budgets are in memory (`backend/src/auth-work-guard.ts`, `backend/src/public-form-guard.ts`). The repository documents that production must use verified proxy CIDRs and stay single-replica until shared rate-limit state is available. Confirm the live ingress rewrites forwarding headers and keep one replica until that assumption changes.

## Strengths worth preserving

- Privileged Windows operations are routed through Rust/Tauri commands; the HUD has a separate, narrower capability set. The no-new-privileges check passed.
- Rollback snapshots and exact technical previews are central to the native design; the next controls should use that infrastructure consistently rather than weakening the contract.
- Backend TLS rejects insecure remote configurations, schema readiness gates API access, and one-time account-action tokens are handled transactionally.
- Quick-install code now selects a specific x64 artifact and checks Authenticode publisher/timestamp before launch; its Windows regression suite still needs to run on Windows.
- CI pins its GitHub Actions by commit SHA and uses least-privilege workflow permissions.
- Performance claims are appropriately restrained; keep measurement on real Windows hardware separate from configuration counts and synthetic model tests.

## Recommended order of work

1. Fix Skinpacks and active Browser Only copy in all six locales; make the copy test and quality gate pass.
2. Correct `CONFIGURABLE_TWEAK_IDS` and verify that every applied switch is counted and included in the intended restore/history flows.
3. Retire legacy keyboard writes without invalidating rollback snapshots, and reconcile each active control’s declared effect with its actual snapshot/write set.
4. Reconcile the original 161-control catalog claim with the active count and all current public and Store copy.
5. Re-run the full Windows CI/release verification, including Rust/native tests, PowerShell quick-installer tests, signed installer checks and PostgreSQL-backed integration tests. Confirm production proxy configuration before scaling.
