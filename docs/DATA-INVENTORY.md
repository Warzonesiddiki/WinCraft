# Where WinCraft keeps personal data

Every table the backend creates is listed here with what it holds, who can read it and what removes a row. The list is checked against the schema by `npm run check:data-inventory` — adding a table without classifying it fails the gate, and so does documenting a retention window the worker does not enforce, so this page cannot quietly go stale.

The rule the schema follows: a row may say who someone is (users, entitlements) or what they did anonymously (download attributions, error reports), never both joined by a column that invites linking them back to a person.

Two mechanisms remove rows, and they answer different questions:

- **When someone leaves.** `backend/src/account-deletion.ts` deletes the account and everything attached to it in one transaction, from the app's own danger zone. It refuses while a subscription is still billing, because deleting our row cannot stop Stripe from charging a card.
- **When nobody leaves.** `backend/src/retention.ts` prunes what is past its window every six hours and once at startup. Every number below appears in that file, and the gate compares the two.

| Table                        | Holds                                                                                        | Retention class | Removed by                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------------------- | -------------------------------------------------------------------------------------------- | --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `users`                      | Email, password hash, names, date of birth, plan, Stripe customer id, token version          | `account`       | Deleted by the account holder with `DELETE /api/account` (password plus a typed confirmation). Operator deletion remains the fallback. `ON DELETE CASCADE` removes the child rows below if an operator deletes one directly.                                                                                                                                                                                      |
| `action_tokens`              | SHA-256 hash of a verification or password-reset link, purpose, expiry                       | `security`      | Deleted with the account, so a link that arrived before deletion cannot be used after it, and purged automatically 7 days after expiry by `backend/src/retention.ts`. A consumed token stops working immediately either way.                                                                                                                                                                                      |
| `billing_receipts`           | Stripe event key, user id, the outbound receipt payload, retry/lease state                   | `billing`       | Deleted with the account. Otherwise kept: a delivered row is the durable record that a receipt was sent, which is what answers "was I told about this charge?". No timer removes it.                                                                                                                                                                                                                              |
| `entitlements`               | Per-product plan and expiry for non-WinCraft products                                        | `entitlement`   | Deleted with the account, or rewritten by a Stripe refund/expiry event.                                                                                                                                                                                                                                                                                                                                           |
| `lifetime_uninstaller_bonus` | Which account activated the lifetime-uninstaller bonus and its expiry                        | `entitlement`   | Deleted with the account.                                                                                                                                                                                                                                                                                                                                                                                         |
| `checkout_reminders`         | When the last abandoned-checkout reminder was sent to an account                             | `billing`       | Deleted with the account. Otherwise one row per account, replaced by the next reminder: deleting it would re-send a nudge inside its own cooldown, so no timer removes it.                                                                                                                                                                                                                                        |
| `reviews`                    | Public review text, display name, optional avatar, confirmation token hash, moderation state | `moderation`    | A submission that was never confirmed is deleted with the account and purged automatically 30 days after its confirmation window closed, by `backend/src/retention.ts`. A published review stays visible — it is public content, not account data — with its address replaced by `deleted+<user id>@wincraft.invalid` and any stored IP and its hash cleared. Operator deletion remains available for moderation. |
| `newsletter_subscribers`     | Email, source form, unsubscribe timestamp                                                    | `marketing`     | Deleting an account marks the address unsubscribed instead of removing the row, so no future mail can reach it and a later re-subscribe is an update rather than a duplicate. Unsubscribing from the site does the same; only an operator removes the row.                                                                                                                                                        |
| `error_reports`              | App, version, free-text context and message from the desktop apps                            | `support`       | Purged automatically 180 days after `created_at` by `backend/src/retention.ts`, or with the account if one is referenced. Deliberately has no user reference, so a report cannot be joined back to an account, and no IP or device identifier is stored with it.                                                                                                                                                  |
| `download_attributions`      | Campaign labels (`utm_*`) and a timestamp for a download click                               | `analytics`     | Purged automatically 400 days after `created_at` by `backend/src/retention.ts`. The window is deliberately wider than the 365-day maximum the operator report offers, so a year-over-year comparison keeps its oldest days. Normally stored: no IP, user agent or identifier, so rows cannot be joined to a person.                                                                                               |

## What this page is not

- It is not a backup or migration plan. Schema changes are applied by the versioned runner in `backend/src/migrations.ts`; every statement is idempotent so an existing installation adopts the new shape without a reset.
- It is not a promise about a specific row's moment of deletion. The worker decides which rows are eligible; a row can outlive its window by up to one run (six hours, or until the next start).
- It is not a substitute for a data-protection review. One thing found while writing it is recorded rather than silently changed: receipt payloads keep the customer-facing text they were sent rather than re-deriving it, which is deliberate for auditability and is why those rows have no timer.
