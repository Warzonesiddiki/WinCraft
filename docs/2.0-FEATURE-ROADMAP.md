# WinCraft 2.0 — competitive feature roadmap

**Date:** 2026-10-17
**Question answered:** what must be added for WinCraft to reach AtlasOS / ReviOS / Tiny11-class results in place, without a custom ISO, and to be the best tool for pure gaming.
**Method:** read the leading projects' published feature sets, then diffed them against what this
repository actually implements. Sources are listed per item.

**Safety-first update (2026-10-17):** exact SvcHost fan-out snapshots and protected-service
exclusions are implemented but still need Rust/Windows validation. Barebone batch operations now
require consent and report per-item failures. Machine-wide package deprovisioning is disabled and
removed from IPC until exact allowlisting and tested recovery are available. These safeguards do
not complete the broader catalog roadmap below.

## 1. Where WinCraft already wins

Nothing below should be traded away to chase a competitor. These are advantages the field does not have:

| Advantage | Why it matters against the field |
| --- | --- |
| Transactional change ledger with before/after values | Atlas/ReviOS playbooks are one-way; Win11Debloat and privacy.sexy are reversible but script-generated; none of them show you the *exact* pre-state per value. |
| Statistical Before & After (7+ runs, rank test, p<0.01) | No competitor measures whether a change did anything. Everyone else publishes a target. |
| Live DPC/ISR tracer with driver attribution | LatencyMon is the reference and is closed-source; Sophia and WinUtil have nothing. |
| Per-build/edition capability gating ("Not available on this PC") | Script tools silently no-op or fail; custom ISOs silently miss. |
| Signed, gated build with 6-locale parity | Sophia is the only other multi-locale project and it is a script module. |

**The differentiator to lean into:** WinCraft is the only one that can say *"here is what this
change wrote, and here is what it measured."* Every gap below should be closed in a way that
keeps that property.

## 3. Tier 1 — required to claim AtlasOS parity (do these for 2.0)

### T1.1 Windows Update control surface

The largest remaining control-surface gap. WinCraft has an update-drift detector and some
individual policies, but not a complete update-management panel. Do not disable servicing or
claim that deferral makes a PC safer; it delays security fixes.

- **Bounded deferrals now ship:** `defer_quality_updates_7_days` writes the Windows Update deferral policy for 7 days. It also defers monthly security fixes, which remain unapplied during the wait; this is not a pause or a disable. `defer_feature_updates_30_days` delays feature-update offers by 30 days while monthly quality/security updates continue. It is not a version pin and does not extend Windows support. Both are reversible, Pro-or-higher controls; Windows behavior still needs VM validation.
- **Driver offers can be excluded:** `exclude_windows_update_drivers` writes `ExcludeWUDriversInQualityUpdate = 1` on Pro-or-higher Windows 10 1607+ and Windows 11. It excludes standalone driver-classified offers from the normal quality-update cycle, not drivers bundled into security/critical updates or dynamically installed during feature updates. Windows Update stays enabled; manage standalone drivers yourself and restore the setting to resume driver offers. Microsoft recommends leaving driver updates allowed by default, so this is an opt-in management preference—not a performance tweak—and still needs VM validation ([policy reference](https://learn.microsoft.com/en-us/windows/deployment/update/waas-configure-wufb)).
- **Scheduled automatic restart while signed in:** `prevent_auto_restart_while_logged_on` now journals and writes `HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU\NoAutoRebootWithLoggedOnUsers = 1`. It does not stop downloads or installation, and a restart-required security update is not fully active until the PC restarts. The control is gated to Pro-or-higher editions and still needs Windows VM validation.
- Pausing quality/feature updates (including the 35-day pause window), Active Hours and target-release/version pinning are not yet configurable. Feature deferral up to 365 days is also not offered; the shipped choice is deliberately limited to 30 days.
- Delivery Optimization's existing `disable_delivery_optimization` control sets `DODownloadMode = 0` (HTTP-only, no peer-to-peer exchange). It does **not** shut down the Delivery Optimization service or Windows Update; keep the service available for Microsoft-hosted downloads.
- `TargetReleaseVersion` / `TargetReleaseVersionInfo` so a user can stay on a known-good build.
- `block_oem_device_apps` already writes `PreventDeviceMetadataFromNetwork`; treat OEM companion-app installation as only partially covered until the exact app-install effect is verified on Windows.
- Each control must be journalled and revertible, state its scope and taking-effect behavior, and state the security trade-off honestly (deferring updates delays security fixes).

### T1.2 ISO / export path — the "custom distribution" experience without the ISO

This is what "similar to AtlasOS/ReviOS/Tiny11" actually means for a tool that runs in place.

- Generate `autounattend.xml` from the user's current selection (Winhance does exactly this via WIMUtil).
- Generate a first-logon script/manifest that replays the same profile on a fresh install.
- Export a signed, self-contained profile bundle (`.wincraft.json` + signature) that another PC imports.
- Optional: offline `install.wim` post-processing for a true custom image, clearly labelled as destructive and out of the reversible ledger.

### T1.3 Apply-to-other-user / default profile / Sysprep

Without this, a tuned PC still provisions bloat for every *new* account, and Windows re-adds
things after a feature update. Win11Debloat ships exactly this (other-user + Sysprep mode);
WinCraft has neither, and no competitor currently combines it with a real rollback ledger.

- Apply HKCU-scoped controls to another local account.
- Apply to the Default user profile (image-wide) after an explicit consent gate.
- Debloat tier that actually removes the provisioned packages (see T1.4) rather than unlinking them.

### T1.4 Re-enable deprovisioning only after safe recovery exists

Machine-wide package deprovisioning is currently **disabled**: its former `dism.exe` table
parser had no rollback journal or supported reinstall path, and it has been removed from IPC
registration and the desktop permission set. Treat this as a deliberate safety boundary, not a
missing toggle. Reintroduce the capability only with exact package identity and allowlisting,
a supported AppX Deployment API path, per-package snapshots and recovery, explicit native
consent, localized risk copy, and tests on supported Windows builds.

### T1.5 Gaming latency suite (the pure-gaming ask)

These are the levers the enthusiast guides use that WinCraft does not expose at all. Each is
high-impact, reversible, and measurable with the engine WinCraft already has:

| Control | Effect | Reversal |
| --- | --- | --- |
| **MSI mode** (Message Signaled Interrupts) for GPU / NIC / USB / audio | Removes legacy line-based interrupt sharing; the most-cited stutter fix | Registry `MSISupported=0` restore |
| **Interrupt affinity** — pin the GPU/NIC ISR off core 0 | Stops interrupts contending with the game's main thread | AFD/interrupt policy restore |
| **Live timer resolution** (`NtSetTimerResolution`, 0.5 ms) | Fixes the 15.6 ms frame-pacing flaw; what TimerResolution/ISLC do | Release on exit |
| **Standby list cleaner with a threshold** — auto-purge when free memory drops below X while a game runs | The ISLC behaviour WinCraft only offers manually | No system state; runtime only |
| **Per-adapter NIC advanced properties** — interrupt moderation, RSS, checksum offload, NIC power-saving off | Real ping/jitter effect on some NICs | Per-adapter snapshot |
| **Per-game auto-profile** — detect the game, apply, revert on exit | GameShift's model; WinCraft has Game Sessions but not whole-profile apply/revert | Session ledger |
| **NVIDIA/AMD driver debloat** — strip telemetry/HD-audio/GFE components on install | NVCleanstall's niche | Documented reinstall |
| **Pro Audio MMCSS task profile** + audio device MSI | DAW/audio dropouts | Task key restore |
| MPO disable, fullscreen-exclusive behaviour, DWM composition tuning | Known micro-stutter fixes on some GPU/driver combos | Registry restore |

**Measurement tie-in:** add a frame-time and input-latency benchmark to the existing Before &
After engine (1% low, p99 frame time, stutter count, click-to-photon where measurable). The
statistical harness already exists; this turns "AtlasOS feels faster" into a number on the
user's own machine — which no competitor can do.

### T1.6 Kernel-integrity proof panel

AtlasOS's loudest criticism is that it disables Core Isolation/HVCI and breaks kernel-level
anti-cheat. WinCraft already claims it never does. Turn the claim into a checkable panel:
read VBS/HVCI/Secure Boot/test-signing/Defender state, display it, refuse any control that
would weaken it, and warn if something *else* weakened it. This is the trust feature that a
competitive player needs before installing anything.

## 4. Tier 2 — depth to be credible as "the" tool

- **Post-apply servicing verification:** after a barebone apply, automatically run `DISM /Online /Cleanup-Image /CheckHealth` + `sfc /verifyonly` and show the verdict, so "WinSxS intact, updates still work" is proven each time rather than asserted.
- **Headless CLI** for imaging, CI and business deployment (WinUtil presets, Sophia functions, Win11Debloat CLI all have this).
- **Data-driven catalog:** move the control table to validated JSON/YAML with a `check:catalog` gate that also feeds `check:public-counts`. This is how the docs stopped matching the build, and how a community can contribute a control without a Rust change.
- **Runtime prerequisites install** via WinGet or direct redistributable: VC++ 2015–2026 x86/x64, .NET Desktop Runtime, DirectX — the actual "get a fresh Windows gaming-ready" step.
- **Optional Windows features:** WSL, Windows Sandbox, Hyper-V, .NET 3.5 — on and off.
- **Software install** via WinGet (browsers, launchers, runtimes), the complement to debloat.
- **App reinstall** from the removal history, not just a Store link.
- **Telemetry IP blocking** (firewall rules / hosts) — the one privacy measure registry policies cannot make, requested of Winhance and shipped by privacy.sexy/WPD. Must be clearly labelled as bypassable-by-change and off by default.
- **DoH configuration** for the major resolvers (Sophia's set), which pairs with the existing DNS control.

## 5. Tier 3 — polish and breadth

- Explorer/taskbar/Start depth: taskbar alignment, button combine mode, snap assist and Snap Layouts, Alt+Tab tabs, last-active-click, drive-letter visibility, hide Home/Gallery/OneDrive nodes, restore common folders to This PC, taskbar search customization, dark mode.
- Laptop: BitLocker auto-device-encryption off, network-off during Modern Standby, GPU transparency off.
- Scheduled maintenance tasks that clean `%SystemRoot%\SoftwareDistribution\Download`, `$WinREAgent`, `$SysReset`, `$GetCurrent`, crash dumps and temp (the set Sophia automates).
- ARM64 (Snapdragon X) verification and per-control availability matrix across Win10 22H2 / Win11 23H2 / 24H2 / 25H2 / Enterprise LTSC / IoT LTSC.
- Build-aware UI: show a per-build availability matrix so users see exactly which of the 150+ controls apply to *their* build before selecting.

## 6. What to add that nobody has (the moat)

Only worth doing if the Tier 1 work is done — but these are what would make WinCraft the
recognised reference rather than another debloat script:

1. **A measured evidence register per control.** Publish, per control, the before/after distributions collected from the Before & After engine across real machines, alongside the current `Measured/Modest/Neutral` tag. Every competitor publishes an opinion; this publishes data.
2. **Input-latency benchmark (click-to-photon).** No open-source tool measures what competitive players actually care about. The DPC tracer + FPS capture already exist; adding a display-latency measurement would be a genuine first.
3. **Update-proofing with automatic re-assertion.** UpdateWatch detects drift; add an opt-in "keep my profile applied" mode that re-applies after a cumulative update, with a diff of what Windows changed and a per-item re-apply gate. This is the answer to the documented fact that Windows reverts tweaks within 1–3 months.
4. **Anti-cheat compatibility certificate.** Run the integrity panel, the servicing verification and the anti-cheat driver check together and emit a signed, timestamped compatibility report.
5. **Playbook interoperability.** Export a profile as an AME-playbook-compatible YAML so an Atlas/Revi user can migrate their tuning to WinCraft and back — meeting the custom-distribution community where it lives instead of competing with it.

## 7. Honest limits to state in the UI

A tool aiming at "perfect for pure gaming" must say what it cannot do, in the same places it
says what it can:

- Firmware/BIOS: C-States, PBO/EXPO/XMP, ReBAR/SAM, per-slot PCIe lane config — not reachable from user mode.
- Kernel and servicing stack: no WinSxS or `System32` file deletion, ever (this is the design choice, and it is the reason Atlas's update breakage does not apply here).
- Anti-cheat: kernel driver behaviour cannot be verified from the app; only Windows' integrity state can.
- No control can guarantee an FPS, latency or battery number; the Before & After result is the only claim.
