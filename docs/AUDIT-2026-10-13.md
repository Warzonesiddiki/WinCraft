# WinCraft: evidence-based audit and optimization plan

**Date:** 2026-10-13  
**Baseline:** commit `015c632cd3b995f16ad938e7f3271d562a8902f3`, version 1.19.0  
**Scope:** React/TypeScript desktop frontend, Tauri/Rust privilege and rollback boundaries, Express/PostgreSQL backend, marketing website, tests, CI and installer bootstrap. Targeted review, not a formal penetration test or exhaustive verification of every Windows API call.

> This is the preserved baseline audit. Subsequent changes and verification are tracked in [the remediation status](AUDIT-FIX-STATUS-2026-10-13.md).

## Executive assessment

The foundations are good: strict TypeScript, lazy-loaded desktop panels/locales, separate HUD permissions, constrained native commands, checked rollback transactions, atomic snapshot replacement, signed updater artifacts, JWT revocation, hashed action tokens, parameterized SQL, durable billing receipts, and meaningful component/accessibility tests.

**Prioritize correctness and trust before adding more tweaks.** The most important current weaknesses are fail-open database TLS configuration, readiness that can go green after schema initialization fails, an account-refresh race, and missing consumer-side verification in the quick installer. Optimization opportunities exist, but there is no measured evidence here for universal FPS, latency, or battery gains.

No critical exploit was established during this audit. That does not establish the absence of critical vulnerabilities. Native Windows behavior, production infrastructure, actual deployed certificates, release binaries and Rust dependency advisories were not verified in this Linux environment.

**Application code was not changed.** This report is the only repository change.

## 2. Prioritized findings

Priority: **P1** = next release/deployment; **P2** = next short iteration; **P3** = planned hardening. Evidence distinguishes reproduced behavior from static inspection and deployment-dependent risks.

### F01 — P1 / High: database certificate verification fails open

**Evidence:** `backend/src/db.ts:22–49`.

- A remote database defaults to `{ rejectUnauthorized: false }` when no CA is provided.
- A configured but unreadable `DATABASE_CA` logs an error and returns `undefined`, silently taking the same insecure path.
- TLS disabling uses `connectionString.includes("localhost")`, not the parsed database hostname. A substring elsewhere in a URL is not a sound transport-security decision.
- Connection-string SSL parameters can also affect the effective `pg` configuration; validate the final behavior rather than assuming the explicit object always wins.

**Reproduction:** Loaded the compiled database module with an unreachable example hostname and a nonexistent CA path, without opening a connection. `pool.options.ssl` was `{"rejectUnauthorized":false}`. This proves the configuration downgrade, not a live MITM attack.

**Change:** Fail startup when an explicitly configured CA cannot be read. Require certificate and hostname verification for production database connections using the system trust store or a provider CA. Parse URLs; allow plaintext only through an explicit local-development policy. Reject conflicting SSL query parameters or normalize them through one configuration function.

**Acceptance:** Tests cover no CA, valid CA, unreadable CA, non-host `localhost` substrings, and conflicting URL SSL settings. A staging PostgreSQL connection rejects a wrong CA and wrong hostname.

### F02 — P1 / High operational risk: readiness can pass after schema initialization fails

**Evidence:** `backend/src/index.ts:111–123,373–400`.

`initSchema()` errors are caught, but `.finally()` starts workers and the HTTP listener anyway. `/ready` only executes `SELECT 1`. A database that accepts queries but rejected a migration can therefore produce a successful readiness response while account or billing tables/columns are missing.

**Change:** Either fail production startup on migration failure or keep the process live while holding readiness at 503 and not starting schema-dependent workers. Prefer versioned migrations under a deployment lock, with an expected schema version checked by readiness. Preserve intentionally unconfigured local development as a separate mode.

**Acceptance:** Inject failure into a migration while allowing `SELECT 1`; readiness must remain 503 and receipt workers must not start. Successful migration transitions readiness to 200.

### F03 — P1 / High supply-chain exposure: quick installer executes downloaded EXEs without verification

**Evidence:** `install.ps1:25–52`; compare `scripts/verify-authenticode.ps1` and `.github/workflows/stable-download-alias.yml`.

The installer chooses the first asset matching `*Setup.exe` **or any `*.exe`**, writes a fixed filename in `%TEMP%`, and executes it. Both normal and fallback paths skip Authenticode/publisher validation. Release CI already verifies signatures, but that is not equivalent to verification on the end user's downloaded bytes.

**Change:** Select an exact supported architecture/installer asset. Use a uniquely created staging directory. Validate Authenticode and the expected publisher, with a documented certificate-rotation policy, immediately before launch. Validate downloaded bytes against an authenticated release manifest when available. Treat verification failures as terminal; do not enter a weaker fallback after a trust failure. Clean up temporary files safely.

Do not rely on an unsigned checksum downloaded from the same potentially compromised release as the only authentication mechanism. Keep the updater's existing signature/version binding.

**Acceptance:** Reject unsigned, wrong-publisher, wrong-architecture, altered and unexpected assets. Exercise normal and fallback paths on Windows. Keep the intentional legacy `PCTweaker-Setup.exe` alias working until consumers are migrated.

### F04 — P2 / Medium: late account responses overwrite logout or a newer login

**Evidence:** `src/App.tsx:248–286,315–339`; `src/lib.ts` renewed-token adoption.

`refreshAccount()` captures a token, awaits the API, then updates account state without checking that the session is still the same. A late 200 can restore the old account's UI after logout; a late 401 can log out a newer session. A renewed header from an obsolete request could also be adopted into a newer session's store if present.

**Reproduction:** Transpiled the exact function extracted from `App.tsx`, used a deferred mocked fetch, logged out, then resolved a successful account response. Final state was `authenticated` for the old account while `readToken()` remained null. This is a UI/session-consistency defect, **not evidence of server authentication bypass**.

**Change:** Track a session generation, abort obsolete requests, and check the captured session before handling 401, renewal or state updates. Deduplicate focus refreshes and apply a modest freshness window. Add a request timeout; other API operations should use the same consistent client policy.

**Acceptance:** Deferred-request tests for logout, account A → account B, late 401, late renewed token, rapid focus events and timeout. No obsolete response may change the current session.

### F05 — P2 / Medium: action-token consumption and account mutation are not atomic

**Evidence:** `backend/src/tokens.ts:39–51`; `backend/src/routes/auth.ts:360–370,488–500`.

The single-use token UPDATE is itself atomic, which is good. But it commits separately from email verification or password update. If the subsequent write fails, or the process exits between operations, the link is burned while the account remains unchanged. Password hashing also happens after consumption.

**Change:** Compute the password hash before entering a short transaction. Use a checked-out `pg` client to consume the token and mutate the account in the same transaction, rolling both back on failure. Do the equivalent for email verification. Send notices only after commit; consider the existing durable outbox pattern for critical account mail.

**Acceptance:** Force the account UPDATE to fail after successful consumption; the token remains usable and no notice is sent. Concurrent consumption still permits exactly one successful account mutation. Verify with real PostgreSQL, not only pg-mem.

### F06 — P1 investigation / deployment-dependent: IP rate limits may be bypassable, and all budgets are instance-local

**Evidence:** `backend/src/index.ts:32,48–54`; `backend/src/routes/auth.ts:29–89`; `backend/src/public-form-guard.ts`.

Repository comments explicitly describe a previously observed Railway/X-Forwarded-For bypass. Current code still uses `trust proxy: 1`, IP-keyed registration limits, and an IP-keyed global limiter. Email-keyed login/reset limits improve per-account protection, but do not bound requests using many different addresses. Anonymous support/review budgets provide a separate backstop, not a global registration/bcrypt budget.

**Not independently verified against the deployed proxy in this audit.** Numeric proxy trust is not automatically vulnerable; actual hop topology and header rewriting decide the outcome.

**Change:** Verify header sanitization at the production ingress using controlled staging requests. Restrict origin access and trust the actual proxy network/topology. Layer per-account, trustworthy source and global work budgets; bound expensive bcrypt/registration work. Use a shared store if adding instances, or explicitly document/enforce the single-instance assumption. Do not use raw attacker-supplied forwarding headers as limiter identity.

**Acceptance:** A staging abuse test rotates X-Forwarded-For and email values, checks source identity, confirms bounded expensive work, and verifies multi-instance limits. Preserve legitimate users sharing a NAT.

### F07 — P2 / Medium safety: reversible settings are conflated with reversible consequences

**Evidence:** `src/components/starter-presets.mjs` Barebone/Office presets; `src-tauri/src/tweaks.rs:225–235`; `src/locales/en.ts:1533–1537`; `install.ps1:10`; README introductory claims.

`auto_end_frozen_tasks` sets `AutoEndTasks=1` and is initially selected within Barebone and Office profiles when those profiles are opened. Its visible description does not explicitly warn about unsaved work. Restoring the registry setting cannot recover work lost when an application was terminated. Likewise file deletion/shredding and cache cleanup must not inherit blanket reversibility claims.

**Change:** Make forced app termination opt-in, explicitly state potential loss of unsaved work, and avoid recommending it in a general productivity profile. Label operations by recovery class: **exact snapshot restore**, **best-effort recovery**, **irreversible**, or **read-only**. Say “supported settings are reversible” rather than “every change is reversible.” Clarify that presets have initial selections within the review screen, even though they are not applied automatically.

**Acceptance:** Every destructive or disruptive operation carries a localized consequence warning and accurate recovery label. Preset regression tests protect the safer selection policy.

### F08 — P2 / Medium quality gap: integration-critical frontend code has no coverage

**Evidence:** generated `coverage/coverage-summary.json`, `vitest.config.ts`, current tests.

Overall line coverage is 46.09%, but `src/App.tsx` and `src/components/account.tsx` both have **0% line coverage**. The global coverage floor therefore does not protect account orchestration, native command dispatch, focus refresh or application-level state transitions. The race in F04 is an example of the gap, not proof that all uncovered code is defective.

**Change:** Add App-level tests around auth lifecycle, apply/rollback, batch partial failure, startup/update and navigation. Add per-file or per-area ratchets for high-risk modules. Supplement jsdom with Windows/WebView integration for CSP, native dialogs, elevation and installer behavior. Run a small PostgreSQL integration suite for transactions/migrations.

**Acceptance:** New tests fail against the current race and token/migration failure behaviors. Coverage gates cannot pass solely because unrelated copy/UI tests increase the global average.

### F09 — P2 / Low release blocker: formatting currently fails CI

**Evidence:** `npm run format:check`; `.github/workflows/checks.yml` enforces it.

**Change:** Format only the four failing locale files using the installed Prettier version; rerun i18n and frontend tests. Keep this change separate from translation wording edits.

**Acceptance:** `npm run format:check` passes, without lowering checks or ignoring locale files.

### F10 — P3 / Low: OAuth callback script is blocked by the backend's own CSP

**Evidence:** global `helmet()` in `backend/src/index.ts:34`, inline script in `/tiktok-callback` at lines 140–152.

Helmet's default script policy does not allow this inline script. The paragraph containing the OAuth code stays empty in a CSP-enforcing browser.

**Change:** Prefer server-rendered escaped text, or an external same-origin script. Keep strong script CSP rather than adding `unsafe-inline`. Mark the response no-store, avoid logging the code, and restrict/disable this one-time tooling endpoint when unused.

**Acceptance:** Browser test under the real response headers shows the code and no CSP violation, with no sensitive value in telemetry.

### F11 — P3 / Low-to-medium reliability: persistent driver cache accepts invalid objects indefinitely

**Evidence:** `src/lib.ts:353–365`; `src/components/hardware.tsx:872`.

A valid date is the only structural check. For example, JSON containing a valid `at` but no usable `audit` is returned as though it were a `DriverAudit`. Storage access before the try/catch can throw, and the cache has no schema version or hardware-change invalidation. Explicit rescan is a useful latency optimization; it should not silently make obsolete diagnostics authoritative.

**Change:** Validate the complete cached shape, add schema version, wrap storage access, show age and stale status, and invalidate on meaningful environment changes. Keep explicit rescan rather than automatically paying the full expensive scan at every launch.

**Acceptance:** Malformed but parseable JSON and blocked storage degrade to “no cache”; old/incompatible entries are marked stale or rejected. An unchanged valid cache still paints immediately.

### F12 — P2 / Low: account welcome still advertises an obsolete free-control count

**Evidence:** `backend/src/routes/auth.ts:22–25` sets `FREE_TWEAK_COUNT = 39`; public-count check reports 141 shipped controls, all free.

The public-count checker passes because the backend welcome constant is outside its current scope. Passing tests that quote whatever count they are given do not establish that the count matches the product.

**Change:** Use one generated catalog summary across public copy and account emails, or remove the fragile number from the email. Extend validation to backend templates/constants.

**Acceptance:** The welcome describes the current all-free product consistently, and a stale backend count fails the check.

### Performance baseline to collect on Windows

Use at least a low-RAM laptop, a mainstream desktop and a gaming/X3D system. Test Windows builds the app claims to support, SSD/NVMe, AC/battery, and with/without supported GPU sensors.

1. Cold launch to first interactive screen, plus p50/p95 for catalog, driver and sensor reads.
2. Five-minute idle, visible dashboard, minimized window and HUD-only runs: process CPU, working set, wakeups and child-process launches.
3. Thirty-minute telemetry run: bounded history, no growing handles/threads, no overlapping expensive collectors.
4. Apply and undo a representative reversible tweak/profile, then compare actual registry/service/power state to the original.
5. Interrupt operations and kill the helper at controlled points; recovery must retain snapshots and accurately report partial completion.
6. Benchmark workload A/B in alternating order with warm-up and repeat runs; report median, dispersion, p95/p99 frame time, power/temperature and tradeoffs, not only “RAM freed.”

Set improvement targets **after** recording the baseline. A smaller bundle or lower used-RAM counter alone is not a user-perceived performance result.

## 4. Windows tweak strategy: improve evidence, not tweak count

### Conservative defaults

- Keep file extensions, UI preferences, unwanted suggestions and startup-app review as transparent opt-in changes.
- Preserve version/hardware compatibility checks and the existing manual-only handling for disabling Memory Integrity. Do not promote security reduction as a default gaming fix.
- Keep snapshot-before-write, checked errors, native-side validation and precise recovery descriptions. A restore point is an additional safeguard, not a substitute for exact rollback.
- Default unknown hardware to neutral/unsupported, not “recommended.”

### Reconsider recommendations and descriptions

| Existing feature                                      | Improvement                                                                                                                                                                                                                  |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `power_plan_performance` / `disable_power_throttling` | `recommend.rs` marks desktops recommended based on form factor. Make this workload-aware or neutral until measured; desktops still pay in energy, heat and noise. Use session-scoped changes with restoration where feasible |
| `disable_startup_delay`                               | Do not call it universally beneficial on SSD/NVMe. Removing delay can shift I/O/CPU contention to the first seconds after login. Measure usable-desktop latency with the user's startup workload                             |
| `priority_separation`                                 | Inspect the current value; skip no-op writes and distinguish an actual change from reapplying a common desktop configuration. Avoid promising broad responsiveness gains without measurement                                 |
| RAM trim / standby purge                              | Keep manual and contextual, not a default periodic optimization. Track pressure, hard faults and subsequent latency; emptied caches can need rebuilding. Current game guards are worth preserving                            |
| `auto_end_frozen_tasks`                               | Remove default selection from productivity-oriented profiles; warn explicitly about unsaved work                                                                                                                             |
| Search/index/background-app controls                  | Present functional costs before application: search availability, notifications, synchronization and app behavior. Hardware alone does not capture those user needs                                                          |
| BBR/network/DNS/affinity/HAGS                         | Require supported hardware/build/workload, capture before/after evidence and retain exact restore. “Advanced experiment” is more accurate than “universal optimization”                                                      |
| “Barebone / Atlas OS level”                           | Avoid equivalence and “zero latency” implications without comparative benchmarks. Describe exactly which settings are changed and what remains untouched                                                                     |

### Valuable feature enhancements

1. **Preview/dry-run for every batch:** exact changes, admin needs, affected apps, restart requirements and recovery class.
2. **Conflict detection:** warn when policy is managed externally or when another tool changed a value since WinCraft's apply. Offer clear choices rather than silently overwriting outside changes.
3. **Verified result states:** distinguish attempted, applied, read-back verified, reboot pending, restored and restore failed.
4. **Evidence metadata per tweak:** supported OS builds, intended workload, known downside, authoritative source, last verification date and benchmark confidence.
5. **Opt-in measured recommendations:** recommend from pressure/workload/preferences, not registry absence or number of unapplied switches. Avoid inflated “issues fixed” counts.
6. **Compatibility migration tests:** exercise preferences, snapshots, profiles and updater behavior from the old product identity. Preserve needed aliases instead of blanket-renaming internal identifiers.

## 5. Corrections to existing audit documents

Treat `AUDIT.md`, `DEEP-AUDIT.md` and the large fix plan as historical inputs, not verified current findings.

- `DEEP-AUDIT.md` calls hundreds of `.unwrap()` occurrences production risks. In the current `rollback.rs`, the `.unwrap()` calls found during inspection are in the test module starting at line 683. Counting test assertions as production crash paths materially overstates risk. Review each production call by reachability and invariant instead of mass replacement.
- Do **not** replace fallible snapshot or registry operations with `unwrap_or_default()` to hide errors. On mutation paths, propagate the failure and make no change when exact recovery cannot be guaranteed.
- A `SAFETY:` comment count is not proof of unsafe-code correctness. For example, `elevation.rs` labels an unsafe block with a ShellExecuteW explanation even though that block queries tokens/SIDs. Review actual pointer lifetimes, alignment, sizes, ownership, cleanup and races; replace generic/inaccurate comments.
- Account refresh is no longer fetching a Pro license in the reviewed App. That old “unnecessary license refresh” recommendation is stale.
- All controls being free is intentional. Do not restore paid gating or remove shared billing compatibility merely because this application no longer charges for features; the backend still supports other products and historical customers.
- `PCTweaker-Setup.exe` is intentionally maintained by the stable-download workflow. Its presence in the installer fallback is not independently a broken rename.
- CORS is not authentication, and release DevTools being disabled is not an IPC security boundary. Keep validation in Rust even when a UI guard already exists.
- Browser storage tokens are accessible to same-origin JavaScript. A long-term hardening option is a narrow native authenticated client with OS-protected credential storage; evaluate complexity and permissions rather than claiming desktop localStorage is inherently safe.
