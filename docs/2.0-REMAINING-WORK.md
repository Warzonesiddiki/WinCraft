## 0. Status after the safety-first pass

The highest-risk controls have been tightened before broadening the tweak catalog:

- SvcHost fan-out now journals exact per-service originals, validates direct service paths and live executable identity, and excludes core RPC and Xbox services. Mock-registry coverage was added; Rust and Windows execution remain unverified.
- Barebone task changes require consent for the exact allowlisted task or batch. Batch results retain failed paths, absent/unreadable task paths, and elevation errors instead of reporting a misleading count.
- Machine-wide package deprovisioning is disabled, removed from IPC registration and the desktop permission set, and remains unavailable until exact allowlisting and tested recovery exist.
- The Startup section is now named **Windows Background Tasks**.

The latest full frontend run passed **404/404 tests across 31 files** (`npm test -- --reporter=dot --maxWorkers=4`). An earlier default-parallel run had one intermittent EcoQoS toggle failure; the focused test and related component suite passed on rerun, so its cause is still unresolved. `npm run build`, lint, formatting, `check:no-new-privileges`, `check:public-counts`, and `check:i18n` passed. This environment has no `cargo`, `rustc`, or `rustfmt`; Rust compilation and Windows-native behavior still require validation on a suitable Windows runner.

## 2. Historical P0/P1 audit findings and remaining feature gaps

### 2.1 The Skinpacks engine was a taskbar-hide stub — **resolved**

**Resolved 2026-10-15.** What ships now is one named transformation, `cosmic_dark`,
written by `src-tauri/src/skinpacks.rs` as **nine per-user `HKCU` values**: dark app and
system surfaces, transparency off, accent colour on title bars and the taskbar, flat
window borders and no minimise animation, and the taskbar at the left. It reads every
original value first and journals the whole set under the rollback id
`skinpack_cosmic_dark` before writing (so it appears in Change history with before/after
values and restores in one click), then broadcasts `WM_SETTINGCHANGE` / `ImmersiveColorSet`
so the shell re-reads its colours without a sign-out. `active` is read back from the
ledger rather than hardcoded, so the panel no longer desynchronises after a relaunch. The
five invented names are gone: `apply_skinpack` rejects any id it does not ship, because a
pack that does not exist cannot be applied. All copy lives in the six locale tables
(`skinpacks.*`), and the panel states in the user's own language that it re-themes Windows
rather than installing COSMIC, GNOME, KDE or macOS. Evidence: 5 Rust tests
(`cargo test skinpacks`, including that the two accent encodings — `0xAABBGGRR` for
`AccentColor`, `0xAARRGGBB` for `ColorizationColor` — still decode to the documented teal)
and 5 component tests in `src/components/skinpacks.test.tsx` (scope copy, apply, restore,
refused apply, and a build with no pack). The unreferenced `assets/skinpacks/` asset is
deleted.

The stub it replaced, kept as the record that motivated the rewrite:

```rust
pub fn apply_skinpack(id: String) -> Result<SkinpackInfo, String> {
    let pack = packs.into_iter().find(|p| p.id == id)...;
    set_windows_taskbar_visible(false)?;   // ShowWindow(FindWindowW("Shell_TrayWnd"), SW_HIDE)
    let mut active = pack;
    active.active = true;
    Ok(active)
}
```

Each of those was verified at the time:

- **The UI describes something else.** `src/components/skinpacks.tsx` tells the user it
  "Replicates Linux COSMIC DE, macOS Sequoia, GNOME 47, and KDE Plasma 6 without patching
  system DLLs or modifying explorer.exe. Revert anytime in under 500ms." No theme, panel,
  dock, menu bar, font or shell is applied — the Windows taskbar is hidden. This directly
  contradicts the project's own published rule that unsupported behaviour is "reported,
  never faked" (README, "Zero compromises").
- **No rollback journal entry.** `apply_skinpack`/`rollback_skinpack` write nothing to the
  change ledger, so the master plan's Definition of Done — "Every registry, service, task,
  and AppX operation records a pre-write snapshot and can be rolled back via the Change
  History ledger" — does not hold for this feature.
- **State is not persisted, so the UI desynchronises.** `available_skinpacks()` hardcodes
  `active: false` for all five, and `list_skinpacks` rebuilds the list on every mount.
  Relaunch the app after applying a skinpack and nothing is marked Active, no "Restore
  Windows Shell" button renders, and the taskbar stays hidden with no in-app way back
  (`handleRestore` is only reachable while `activeId` is set).
- **Hardcoded English violates the six-locale invariant.** `grep -c skinpack src/locales/en.ts`
  → `0`. Every string in the panel is inline English, plus toast copy
  (`"Applied ${name} overlay. Windows Taskbar suppressed safely."`). `check:i18n` cannot
  catch this: it only compares keys that exist. `docs/VIBE-CODING-GUIDE.md:16` states the
  invariant as non-negotiable.
- **Dead asset.** `assets/skinpacks/cosmic/glazewm.yaml` exists and is referenced by
  nothing (`grep -rn glazewm --include=*.rs --include=*.ts --include=*.tsx --include=*.json`
  → no matches).
- **No tests.** `skinpacks.test.tsx` does not exist.

The spec it claimed to implement (`docs/research/skinpacks/POPULAR_SKINPACKS_CATALOG_SPEC.md`,
804 + 979 lines) named Zebar as the shell engine and described window-level hooks
(`WS_EX_LAYERED | WS_EX_NOACTIVATE`, `EnumWindows`); `grep` finds **zero** references to
Zebar, acrylic, or traffic-light controls in `src/` or `src-tauri/src/`.

### 2.2 Runtime ETW autologger teardown — **partially implemented; verification open**

`docs/WINCRAFT-2.0-ULTIMATE-MASTER-PLAN.md` §2.2 specifies in-memory teardown via
`ControlTraceW(..., EVENT_TRACE_CONTROL_STOP)` for `AutoLogger-Diagtrack-Listener`,
`SQMLogger`, `AITEventLog`, `DiagLog`, and `WiFiSession`. The current tweak path writes the
registry setting and then invokes `logman stop <session> -ets`, but discards both spawn
errors and nonzero exit status. Rollback restores the registry value without verifying or
restarting the runtime session. The README and CHANGELOG call these "5 ETW Autologger session
teardowns"; report and test these partial outcomes before describing the controls as reliable
teardown.

### 2.3 SvcHostSplit fan-out safety — **implemented; Windows validation outstanding**

The SvcHost fan-out now excludes core RPC services and `Xbl*`/`Xbox*` names, identifies the executable token in each `ImagePath`, and journals the exact original `SvcHostSplitDisable` state per service before writing. Rollback validates the journal target and restores only values that have not drifted externally. Mock-registry tests cover exact restoration, partial failure, and drift. Rust tests and supported-Windows VM validation have not run in this environment.

### 2.4 Machine-wide deprovisioning — **disabled pending a safe recovery design**

The previous implementation shelled out to `dism.exe` and parsed human-readable table output without a rollback journal or supported reinstall path. That implementation is removed: the command is no longer IPC-registered or granted by the desktop permission set, and the remaining function is a disabled stub. Do not restore this capability until package identity is exact, the allowlist is explicit, changes are journaled, and recovery is tested across supported Windows builds.

### 2.5 The 1-Click Command Deck still ships one preset

`docs/research/FRONTEND_UIUX_OVERHAUL_SPEC.md` §1.2 promises immediate presets
(`AtlasOS Ultra`, `ReviOS Balanced`, `Tiny11 Minimal`, `Barebone Lean`) "with clear process
count targets and real-time visual delta feedback".

`src/components/command-deck-hero.tsx` still exposes one `ATLAS_TWEAK_IDS` profile. A

### 2.6 Windows Update control surface — **partial; native behavior unverified**

Four reversible Windows Update policy controls are now declared in `settings_tweaks.rs`.
`prevent_auto_restart_while_logged_on` writes
`HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate\AU\NoAutoRebootWithLoggedOnUsers = 1`;
`defer_quality_updates_7_days` enables the quality-update deferral and sets its period to 7 days;
`defer_feature_updates_30_days` enables the feature-update deferral and sets its period to
30 days; `exclude_windows_update_drivers` sets
`ExcludeWUDriversInQualityUpdate = 1`. All four are machine-scoped and Pro-or-higher gated;
the deferral and driver policies require Windows 10 build 14393 (1607) or later. The quality
deferral delays security fixes, which remain unapplied during the wait; the feature deferral
leaves monthly quality/security updates on schedule, is not a version pin, and does not extend
OS support. Driver exclusion only withholds standalone driver-classified offers from the
normal quality-update cycle: drivers bundled into critical/security updates or dynamically
installed during feature updates can still arrive. Users must manage standalone drivers
themselves. The signed-in restart control likewise does not stop updates, and a restart-required
security fix is not fully active until reboot. All six locales describe these trade-offs.

Rust tests pin policy values, scope, edition gating, snapshot shape and caveats; the VM matrix
now expects Pro/Education and Windows 10 Pro to apply and Home to refuse. Rust and Windows
behavior were not verified here. Pause, Active Hours and target-release/version controls remain
missing. `disable_delivery_optimization` is peer-sharing-only (`DODownloadMode = 0`, HTTP-only);
it does not disable the update service or Microsoft-hosted downloads. The driver policy is an
update-management preference, not a performance tweak; no speed or resource gain is claimed.
